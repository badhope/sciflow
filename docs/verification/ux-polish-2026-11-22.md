## 一、这轮补了什么

### 1. 研究循环审批：先看方案，再决定批不批

`ResearchCycleRunner` 在 `awaiting_approval` 状态下默认展开“待批研究方案”，直接渲染 `pendingProtocol.design`。共享组件 `StructuredDetails` 把人话标签、数组、嵌套对象和超长 JSON 分开处理，协议里的目标、变量、样本、分析、风险、步骤和参考依据都能在审批区读完。

真实验收时启动了人工审批 cycle `3630dff6-f161-440a-b665-7900d26af055`，页面进入待批态并显示 7 项方案，协议版本 1，协议 id 前 8 位 `51fb80a7`。该 cycle 只为界面取证而建，验收后已手动置为 `stopped`，不进入正式研究执行。

如果服务端没有返回 `pendingProtocol.design`，页面会提示“服务端没有返回方案正文，不要盲目批准”，不再给一个只有标题的空壳。

### 2. 工具调用卡：从装饰性绿勾改成真实结果

AI transport 在发起 `tool-call` 时记录时间，收到 `tool-result`、`tool-error`、`tool-output-denied` 时下发 `tool_result` SSE。字段包含 `id`、`name`、`status`、`duration_ms`、`output` 或 `error`、`output_chars`；输出超过 1600 字符会截断，但保留真实长度。

服务端 `forwardOpenAiSse` 补上了 `tool_result` 透传。前端 `streamChat` 解析事件，`chat-session.ts` 按工具调用 id 回填。`MessageList` 的工具卡现在区分运行中、成功、失败、拒绝；旧会话没有结果事件时显示“状态未记录”，不再默认绿色勾。

真实模型调用 `project.list` 的 SSE 已收到：

```text
id: call_00_IaO99CMi2bmUKdA4yGk7063
tool: project_list
status: ok
duration_ms: 19
usage: prompt 14192 / completion 308 / total 14500
```

对应 Agent run 的步骤链记录为 `tool:project.list`，耗时 6ms。工具卡的成功、失败、无记录三态由 `MessageList.tool-calls.test.tsx` 覆盖。

### 3. Agent 执行历史：从摘要列表下钻到步骤链

`AgentOpsPanel` 的最近执行改用已有 `api.agent.executions(projectId, 10)`；点击某一条后按需调用 `api.agent.getRun(runId)`，打开“执行详情”弹窗，展示来源、模型、时间、耗时、token、输入/输出摘要、错误原因和逐步步骤链。每一步还能继续展开输入与输出。

真实项目驾驶舱已点开验证：

```text
chat / deepseek-v4.1-flash / 0.2s / 0 tokens
步骤链 1 步
#0 tool:project.list / 6ms
输入：请调用 project.list 工具列出当前项目的项目列表……
输出摘要：chat 工具会话（57 个工具可用）
```

`AgentExecution.totalTokens` 在 UI 映射为 `tokens`，所以真实示例显示 0 tokens 不一定代表执行失败。

### 4. 计划审批卡：正文和工具白名单一起可见

`PlanApprovalCard` 与 `AgentOpsPanel` 的待批计划都渲染 `plan.plan`，复用 `StructuredDetails` 展示研究问题、假设、风险、预计产出等字段。审批人不再只看到 title、summary、工具白名单和步数。

### 5. 长篇章节：能打开读，也能控制连写数量

`LongformPage` 的章节卡片整体可点击，支持键盘 Enter/Space。打开后是一个只读弹窗，包含状态、字数、目标、错误、完整正文、本章摘要，并提供“复制正文”和“下载本章 Markdown”。`GET books/:id` 本来就带 `content`，这条链路没有新增后端接口。

连写数量从写死的 3 章改成 1–50 的数字输入，调用已有 `POST /books/:id/write` 的 `count`。批量结果读取真实 `failures`，失败章节和原因会列出来；`pending=0` 但 `failed>0` 时仍可重试。

真实浏览器在《雾港来信》上验到 2 章、1608 字；第 1 章弹窗显示 691 字全文、复制和下载按钮；连写数量填 5 后按钮变为“连写 5 章”。

### 6. 投稿 readiness：缺什么补什么，期刊名贯穿全流程

`SubmissionReadinessPanel` 新增纯函数 `insertMissingSubmissionBlocks`，只补缺失的 `## 摘要` 和 `## 关键词`，不覆盖已有内容；有首个 H1 时插在标题之后，否则置顶。点击“生成并插入”后调用已有 `api.documents.abstract`，拿到摘要和关键词再 `api.documents.update` 回填，随后重跑 readiness 并失效文档 query。

期刊状态从面板局部 state 提升到 `SubmissionPage` 的共享 `journal`。`pickJournalToSubmit` 同时写入登记表单、Cover Letter 与投稿包，避免三个 Tab 各填一次。

真实浏览器使用临时稿“验收临时稿：摘要关键词补齐”做了完整点击：

- 插入前：ready 57%，摘要块和关键词块均为“提醒”，页面出现“可补齐：摘要块、关键词块”和“生成并插入”。
- 首次点击遇到上游模型 502；页面把错误原样呈现出来，没有假装成功。
- 重试成功，接口返回 201，摘要和关键词写入正文。
- 插入后：ready 65%，摘要块和关键词块转为“通过”，补齐提示消失，正文从 2122 字增至 2367 字。
- 临时稿剩余的两个阻塞来自它自身没有 citation 表，不是补齐逻辑引入的问题。取证后临时稿已删除。

期刊联动用“软件学报”做了真实点击：

- 期刊推荐点“投它”后，页面提示“已把「软件学报」带入登记表单、Cover Letter 与投稿包”。
- 投稿跟踪的期刊名：`软件学报`
- Cover Letter 的目标期刊：`软件学报`
- 就绪检查的目标期刊：`软件学报`

## 四、还没拍板的产品口径

这些不是本轮代码缺陷，是产品选择：

1. LLM 评审是否纳入质量门禁。当前客观检查是硬门，LLM 评审只作为参考。
2. readiness 是否从“草稿迭代”标准升级为“投稿标准”。当前默认仍是 70 分、2000 字、4 章节、5 条唯一引用。
3. 研究循环空响应时的 `deterministicProxyCode()` 兜底是否算正式产品行为。当前它能让循环继续，但不应被误读成模型产出了完整方案。

## 五、既有边界

- 桌面重启后远程控制不会自动恢复。
- 公网访问需要 `SCIFLOW_REMOTE_PUBLIC_URL` 和外部 HTTPS 反代。
- 没有局域网地址时，远程二维码可能一直停在“生成中”。
- 远程控制弹窗仍缺独立前端单测。
