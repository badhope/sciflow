第一次把真实模型放进研究循环，它翻车得很安静。

我问它：二维晶格热导率和同位素质量缺陷之间，到底有没有稳定的相关关系。它很快写出一份看起来像模像样的协议，变量、假设、实验步骤一应俱全。然后 Critic 只回了一行：严重偏离原问题。它把“晶格热导率”写成了通用的误差/不确定性相关性，字都认识，意思已经跑到另一个课题去了。

那一刻我盯着屏幕，想起自己写论文被导师打回来的样子。导师不会替你重写，但他会告诉你哪里不对。问题是，一个只会顺从的助手，连“哪里不对”都接不住。

不是让模型再答一遍，而是让门禁把错误变成输入

最早的版本是单 Agent。它提假设、写协议、跑实验、写结论，一条线走到底。提示词写得很细，结果还是很吃运气：遇到不懂的地方，它会用更漂亮的措辞把空白盖住。

后来我把角色拆开：PI 负责把问题变成可执行协议，实验者只负责按协议跑沙箱，Critic 只看真实输出和证据，另有一个独立专家在协议进入沙箱前审批。关键不在“多几个 Agent”，而在协议必须写清那些平时最容易糊弄过去的东西：

· 样本量是多少，训练/测试怎么分；
· X 的维度、分布、是否有异方差；
· 树的数量、最大深度、随机种子；
· 统计检验用哪种 bootstrap，置信区间怎么算；
· 什么结果算支持，什么结果算驳回。

写不清就不让跑。专家驳回后，门禁不是把协议原样丢回给 PI 说“再试一次”，而是把驳回理由作为下一版的设计输入，自动重写，最多两版。两版还不过，整轮停下，留一个可审计的失败状态。

这条回边听起来很朴素，效果比换更大的模型明显。模型不需要一次答对，它需要知道“错了之后往哪里改”。

真实跑起来是什么样

1.19.18 里，这不是概念演示。只给一个研究问题，真实网关连续跑完两轮：

· cycle5 230db717-bbd0-42c2-be8c-397775c75a61：PI 协议 → 专家批准 → 沙箱执行 981 ms → Critic supported / confidence 95 → synthesize，22,199 tokens。
· cycle6 582f9dad-c625-4817-92d3-9b3eb0d3594a：同一问题在重建后的服务上再跑一遍，沙箱 745 ms，Critic 仍是 supported / 95，16,681 tokens。

统计结果不是“看起来相关”。cycle6 里，σ=0.05 那组 r=0.996290，置信区间 [0.996266, 0.996313]；σ=2 那组 r=0.279082。前者几乎贴着上界，后者明显掉下来。这个差异被写进 claim，claim 再指回 run、stdout 和证据行。你不信，可以自己翻。

更有意思的是失败样本。cycle2 的 bootstrap CI 下限是 0.162，低于预设的 0.2，Critic 判 refuted；cycle3 专家第一次驳回，门禁自动重写，第二轮以 confidence 88 批准，沙箱跑完，Critic 因为 r=-0.0116 又判 refuted。这些轮次都停在 max_iterations，没有硬拗成“成功”。

一个科研助手最该学会的，可能不是怎么把话说满，而是怎么在证据不够的时候停手。

为什么这条回边难写

难的不是 LangGraph 的边，难的是状态。

研究循环不是一次 HTTP 请求。它会在审批节点挂起，等几十分钟甚至更久；沙箱可能跑几分钟；服务可能被 kill -9；模型网关可能突然空响应。只要有一个环节把“内存里的 running”当成真相，重启后就会留下永远不结束的循环。

所以我们把 checkpoint 和业务数据放进同一个 SQLite，启动时先捞上次残留的执行中循环：有断点就续跑，没有就标 blocked；另有一个看门狗，超过设定时间没有节点心跳就释放运行锁，让人可以从断点手动恢复。协议审批用 LangGraph 的 interrupt 挂起，批准后用 Command({resume}) 续跑，不是重新开一轮。

这些听起来像运维细节，但它们决定了一个“全自动科研”能不能真的离开你的终端窗口。

它现在仍然不完美

真实网关还是会间歇空响应。我们做了结构化输出的键名归一化和模型降级链，主模型三次重试还不行就切备选模型；再不行就 fail-closed 到 blocked，不编结果。这个边界写在证据文件里，不藏在宣传语里。

它也还不是“什么课题都能跑”。目前的强项是有明确变量、可沙箱执行、能用统计量判定支持/驳回的问题。纯理论推导、需要实验台、需要长期田野调查的课题，仍需要人把问题拆到可执行粒度。

但至少，它不再是一个你问一句、它顺着答一句的聊天框。它会提假设，会写协议，会在沙箱里跑，会被驳回，会改，然后把结论和证据一起留在本地。
